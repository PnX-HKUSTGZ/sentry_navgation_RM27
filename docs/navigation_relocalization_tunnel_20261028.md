## 保留的修复

1. **先恢复朝向再激活导航。** 生成节点发布实际接受的 `/simulation/spawn_pose`；它只决定仿真出生和最终朝向请求，不参与全局匹配初值。定位交接确认后进入 `ALIGNING_HEADING`，基于确认后的 TF 转回所选方向，停稳再释放底盘控制。数据失效、旋转空间不足或位置漂移时停车并禁止交接。
2. **任务内保持巡航朝向。** 仿真开启 `minco_optimizer.hold_cruise_heading`，抑制不断接受坡道朝向漂移的情况。新目标清除参考，终点朝向仍使用原有优化；旋转和位移都保留足迹检查。
3. **保留有用的局部绕行前缀。** 远端未知不再使已经验证的近端修复整体作废。推进量沿原路线计算，必须增加超过 0.20 m，且每条连接完整通过检查；前缀末端仍停车。
4. **修复先验高程的微小倾斜处理。** 配置允许的微小 roll/pitch 不再被第二个固定 `1e-5 rad` 条件拒绝；使用完整旋转计算地面高度，边界不确定时返回无支持。未启用高程约束时，高程数据的存在不再绕过障碍确认。

车高仍为 0.240 m；没有缩小碰撞体或放行低于车高的回波。

## 排除的方案与限制

- 先验地面强约束试验出现未知区域爬行/超时，未采用。
- 仅对横梁启用先验地面参考的试验，四目标总耗时 96.70 s，南洞去/回低速段 1.14/1.38 s，没有改善，已移除该候选功能。
- 将仿真 `p_miss` 从 0.45 改为 0.35 的试验出现首段绕行，四目标耗时 105.78 s，未采用。
- 增加雷达环数的试验未改善首次过洞，最终仍为 360×192。
- 可视网格抽样净高约 0.250 m；原始雷达采样存在少量偏低点。当前证据不能把所有低点都归为虚假障碍，也不能通过降低车高门槛消除所有减速。

本次采用 Gazebo 物理驱动、原始雷达/IMU 全局初始化，以及原仿真的 Gazebo 相对里程计导航。真值只用于验收对照，不输入全局定位搜索；这不是 Point-LIO 连续定位或实车验证。

## 复现与记录

交互使用：

```bash
bash tools/global_relocalization/navigate.bash
```

等待地图，使用 **2D Pose Estimate** 拖动指定位置和朝向，等待 `READY` 后发送 **Nav2 Goal**。
也可加载 `tools/global_relocalization/environment.bash` 后使用原 launch 命令并增加 `global_relocalization:=true`。

自动验收使用独立 ROS domain，启动无界面仿真后运行：

```bash
source tools/global_relocalization/environment.bash
export ROS_DOMAIN_ID=105
python3 tools/navigation_benchmark/relocalization_trial.py \
  --output /tmp/rm27_relocalization_trial \
  --goals '[[7.44,1.673],[-7.231,1.55],[9.201,3.958],[-13.66,-1.64]]'
```

输出目录必须不存在，仿真进程须使用同一 domain；每次使用独立 Gazebo partition。
`startup.json` 在状态转换和每个目标结束时原子保存，`run_*.json` 保存轨迹、命令和诊断；
可选 `--capture-scans` 只保存抽样 NPZ，不是完整 rosbag。

本机完整试验、失败记录、日志及扫描抽样位于
`tools/global_relocalization/.build/tunnel_fix_20261028/`。
`relocalization_report.py` 汇总成功和失败记录；洞内低速定义为真值平动速度 ≤0.2 m/s，
区域定义沿用 `scenario_south.json`，不把绕行未穿洞计作成功过洞。
