# 本轮导航与仿真调试总记录

整理日期：2026-10-10。覆盖本对话中的实车、MINCO、坡洞通行、Gazebo 场地和车辆模型问题。

这份文档按问题归并重复排查，区分已实现的改动、已经过特定路线验证的结果，以及仍未闭环的问题。依据当前代码、配置、已有调试文档及日志整理；无法复核的早期具体改动不作已修复承诺。本次整理只新增文档，不修改导航代码、地图、模型或用户参数。

## 1. 当前进展

系统已经具备独立的实车/仿真 MINCO 配置、无先验高程的坡面识别、原始 PGM 多边形静态检查、有限静态重叠容差、受限脱困、连续上坡助力，以及新的低矮车辆和场地碰撞模型。

南北洞口都出现过成功往返的验证，最新一次用户运行记录有 9 个目标成功。但还不能说任意起点、姿态、观测条件下都能顺畅通过：局部地面未确认、极短安全前缀、优化器候选失败及个别起步不动仍有记录。仿真验证也不能替代实车验证。

## 2. 参数文件与模式整理

**遇到的问题：** MINCO 同时涉及 `nav2_params.yaml` 和 `minco_params.yaml`，不清楚改哪份才生效；曾提出全部集中到实车文件，随后明确要求实车、仿真各自独立；不再需要 shadow 模式。

**当前方案：**

- 实车 MINCO 使用 `src/pb2025_nav_bringup/config/reality/minco_params.yaml`。
- 仿真 MINCO 使用 `src/pb2025_nav_bringup/config/simulation/minco_params.yaml`。
- 对应 MINCO 文件包含 controller、planner、costmap 等完整节点参数，不再靠叠加另一份 Nav2 参数补齐。
- 启动入口只接受 `legacy`、`minco`；legacy 保留对应环境的 `nav2_params.yaml`。旧 shadow 工作流不再作为支持模式。
- “单一参数文件”指导航配置入口，URDF、世界模型、PGM 和高程资产仍是独立文件。启动时的必要参数重写也仍然存在。

调参说明已整理在 [实车调参教程](minco_reality_tuning_guide.md)。其中历史数值需要与当前 YAML 对照，不能当作始终最新的参数表。

对话中还出现过 navigation 无法启动。这与“节点正常运行但车不走”是两类故障：前者需要核对完整参数文件、模式选择、插件及消息编译安装、节点配置/激活错误；后者再沿感知、规划、指令和物理接触排查。现有资料不足以复原每次早期启动失败的唯一原因，不把它们统一归因于车高或未知格开关。最新运行可以完成多个目标，说明该轮已正常进入导航流程。

## 3. 高度、净空、未知格到底代表什么

**遇到的问题：** 障碍物识别高度是不是离地高度、MINCO 能过多高的洞、已观测净空比例含义、`unknown_as_occupied: false` 后为什么仍不动。

**结论与处理：**

- Nav2 点云高度过滤、ROG 点云 Z 裁剪、局部地面高度和车身净空是不同层次。不能把所有 Z 参数都理解成“距当前位置地面”。必须结合处理坐标系和雷达外参判断。
- `projection.vehicle_height` 是相对当地地面的车身高度需求；`headroom_margin` 增加垂直余量。体素高度修正也会影响最终判定。
- `min_headroom_known_ratio` 限制车身体积高度区间里有多少已观测证据。降低它可以减少观测不足造成的拒绝，但不能把已测得的低洞顶、实体障碍变成可通行。
- `unknown_as_occupied`、`clearance_unknown_as_occupied` 分别参与相应地图/净空处理，不是导航总开关。
- 后来增加了 `MincoPlanner.allow_unknown_motion`，明确控制局部安全检查是否接受 ROG 未知格。当前实车、仿真文件都为 `true`。
- 未知格放行仍不能绕过原始静态障碍、真实低净空、需要确认当地地面的洞顶状态、无效查询及地图过期保护。

因此，“未知格允许移动”不等于“所有不确定的洞口都允许移动”。

## 4. RViz 显示与标点

| 问题 | 对应处理或结论 |
| --- | --- |
| 全局路径像直线，只能看到局部轨迹 | MINCO 的 Nav2 接口路径与实际内部全局搜索结果要分开看；关注 `/astar_path_vis`、`/opt_path_vis`、`/minco/opt_path`，不能仅凭 `/plan` 的两点连线判断规划器没有搜索 |
| 动态障碍没有膨胀显示 | 将 ROG 实测障碍接入对应 costmap 动态层，由后续 inflation layer 生成膨胀；同时核对 RViz 显示的是哪一张地图 |
| 靠近后膨胀消失，远离后恢复 | 检查并调整静态层、动态自由观测和膨胀层的组合，避免动态清空误擦静态保护；后续静态通行检查已统一到原始 PGM |
| 地面显示黄色，想改白色 | 属于 RViz 点云颜色变换/固定颜色设置，和导航是否视为障碍是两回事 |
| `/click_point`、`/clicked_poin` 没有输出 | RViz Publish Point 默认通常使用 `/clicked_point`；以工具实际配置为准 |
| RViz 没有 Publish Point | 通过 Add Tool 添加 `rviz_default_plugins/PublishPoint`；本次检查默认 RViz 文件仍未保存这个工具，不能认为已经永久写入配置 |

标点命令可以显式指定消息类型，避免尚无发布者时无法推断类型：

```bash
ros2 topic echo /clicked_point geometry_msgs/msg/PointStamped
```

点选结果必须检查 `header.frame_id`。点击得到的 Z 不应直接代替坡度、真实洞高的测量。

## 5. 实车运动方向、云台转动和起步犹豫

**遇到的问题：** 实车运动方向相反；发出 goal 后长时间不走；转动云台、补到路径观测后又立即移动；希望导航时缓慢转动云台持续观察。

对应处理分成两类：

1. 运动方向需要核对驱动坐标约定、底盘与云台 TF，以及 `src/fake_vel_transform/src/fake_vel_transform.cpp` 的速度变换。不能不核对坐标就整体取反。现有资料不足以确认早期方向故障最终是哪一项修正，因此不把它列为已验证闭环。
2. 有全局路径却不走，可能是局部轨迹没有获得足够有效观测，或 MPC 起步参考太小。后续分别处理观测保持、地面连通、未知格策略、短前缀重规划与控制器启动死锁。

对持续转动的云台，重点是让地图证据在合理时间内保持有效，并正确区分底盘朝向与雷达/云台朝向。它不是单纯把速度上限调大就能解决的问题，也不能无限保留旧观测。

## 6. 先验高程与无先验上下坡

**遇到的问题：** `require_ground_support` 是否会强制使用高程；能否把坡当平地；先验高程怎么制作；能否只用 PCD 和 PGM；如何填写短坡 patch；map 和 PCD 是否默认同坐标。

### 高程先验方案

- `RMUC2026_elevation.pgm` 存储每个 XY 格子的地面高度，是 2.5D 地面先验，不能同时完整表达地面、洞顶和桥下多层空间。
- 当前地图 YAML 的转换为 `z = 像素值 × 0.001 - 1.0` 米，`65535` 为无数据；分辨率 0.05 米，原点 `[-14.6, -5.86, 0]`。
- 仿真生成脚本位于 `src/pb2025_nav_bringup/tools/generate_rmuc2026_elevation.py`。它依赖场地几何及其坐标关系；更换场地后不能假定旧生成器仍直接兼容，已有测试记录包含该问题。
- 实车可从已配准 PCD 提取地面，再投影到与 PGM 相同的分辨率、原点和坐标系。普通占据 PGM 本身没有地面高度，不能单独恢复坡面。
- 简单坡 patch 使用范围、参考点和斜率表达平面：`z = z0 + a(x-x0) + b(y-y0)`。先点击确定 XY 范围，再测高度/坡度并核对坐标，是可行工作流程。
- PCD 与 map 坐标可能一致，但不是格式自带保证；要核对地图生成、定位和 TF 所使用的变换。

### 无先验高程方案

当前实车与仿真都按不依赖高程先验的方向配置。此前提到的三个相关开关分别是：

- `rog_map.projection.prior_map.require_ground_support`。
- `rog_map.projection.near_field_prior_fill_enable`。
- `priormap.ground_edge_avoidance.enable`。

当前均关闭对应先验地面依赖。`require_ground_support: false` 不会取消全部坡度、台阶、断崖和洞顶检查；也不是把所有坡面无条件视作水平地面。切回高程方案还必须提供准确的高程数据，不能只机械地翻转三个布尔值。

### 在线坡面识别的改进

- 参考 `terrain_analysis` 的稳健地面估计思路，利用低分位地面样本、邻域平面拟合、残差限制和姿态补偿，减少局部跳变带来的高度错误。
- `ground_seed_tolerance` 从 0.15 调到 0.18 后，用户观察到长时间卡坡减轻；但后续日志证明这一个参数不能解决所有停车。
- 调整种子半径，使有效地面连通范围覆盖局部前视、车身和地图处理延迟。
- 将原始净空观测证据与最终连通结果分开保存，避免增量更新把“暂时未连通”永久当成“没有净空证据”。
- 新增短时地面连通保持：同格地面和净空仍有效才可沿用；不能自续期、不能以保持格继续扩散；新障碍、高度变化或地面丢失会使其失效。仿真保持 0.8 秒，实车当前关闭。

## 7. MPC 起步死锁、短坡速度不足和频繁放弃目标

**遇到的问题：** `cmd_vel` 只有 0.1 左右；起步卡顿后逐渐正常；短坡需要至少约 0.6 m/s；调整上限后仍慢；经常放弃 goal。

主要处理：

- 对近零参考速度导致的起步循环，增加受约束的参考前探和启动最低指令辅助。
- 上坡辅助从一次性启动补偿改为结合坡度连续过渡，减少助力开关反复切换；参考速度、方向和模式仍参与启用条件。
- 冷启动方向判定参考前方一段路线，不再只看几厘米的横向纠偏段，减少正在前进时被当作反向运动并清零起点速度。
- 将此前写死的热启动判定值参数化：`tracking_error_base`、`velocity_error_threshold`、`direction_cosine_threshold`，两份配置均可独立调整。
- 调整进度检查、目标完成和规划失败等待之间的配合，减少短暂受阻就放弃目标；真实长期无进度仍需要处理阻挡原因。

这些“最低速度”是有条件的指令辅助，不是全程实际速度保底。接近目标、保护停止、平滑刹停、限幅和物理接触都可能让速度更低。特别是实车当前上坡辅助值 0.90 m/s、坡面限速 0.80 m/s，不能据此宣称实车一定输出至少 0.90 m/s。

## 8. 怪异路径、重规划抖动和运动不顺畅

多次日志显示它们不是单一原因：

| 原因 | 已实施的处理 |
| --- | --- |
| 全局认为可过，局部却认为撞墙 | 静态检查统一原始 PGM；全局实测障碍也检查完整车身角部 |
| 通过窄洞时提前转向目标姿态，角部扫到柱子 | 调整局部 yaw 策略，区分全向平移方向与车头朝向，检查固定朝向候选 |
| 路点安全但路点之间曲线贴墙 | 增加整段曲线相对引导线的横向代价，修正局部末端速度方向 |
| MPC 横向误差作用方向不对 | 按路径平移方向分解纵横误差，修正权重旋转矩阵；仿真增大 `q_cross` |
| 短轨迹被时间缩放拉成几十秒 | 非零边界速度下重新优化并加强动力学验证，避免盲目整体拉长时间 |
| 正常换轨迹时突然输出零速 | 求解期间收到同任务正常新轨迹时用新数据重算一次；任务切换、BLOCK 和过期数据仍停止 |
| 远处某格刚变危险就直接急停 | 当前车身和刹停全过程安全时发布独立 `BRAKING_COMMAND`，边平滑刹停边重规划 |
| 一直生成几厘米停车前缀却不换全局路线 | 根据可通行距离、速度和制动需求提前请求全局刷新 |
| 栅格中心不安全，但实际起点安全 | 允许受限的原始起点接入段，沿途仍检查完整车身，不用危险格中心替代真实姿态 |

同时按仿真底盘响应调整预测时间和延迟补偿；靠障碍时主动降低轨迹目标速度以改善跟踪。它会让局部最高速度下降，但目标是减少撞边和停车带来的平均速度损失。

这些处理有明确回归和路线测试，但最新日志仍有优化失败、轨迹截断和制动，不能宣称抖动已经完全消失。

## 9. 静态边界重复栅格化，为什么白格也被挡住

**用户典型路线：** 北侧从 `(-2.322, 7.351)` 到 `(1.909, 7.435)`，中间有 250 mm 高洞口与坡道。

原始 PGM 的该处有效通道约 650 mm，比口述实体洞宽 800 mm 更窄。ROG 对 PGM 做保守投影后，再把结果回填给全局图，叠加膨胀和车身检查，可能封住最后一行可通行车身中心格。

最终采用的方案是：

1. 从原始 `static_layer` 读取 PGM，不把混合后的 master costmap 或 ROG 保守先验投影再当静态原图。
2. 全局搜索、局部轨迹验证、轨迹复用和脱困使用同一套带朝向车身多边形与原始障碍格方块的相交检查。
3. ROG 独立提供实测障碍、未知区域、地面连通和洞顶净空。静态和动态来源必须区分，混合格不能整体忽略。
4. 满足静态精确检查且能区分动态来源时，去掉重复的静态硬膨胀封锁，保留软代价和动态保护。
5. 移除额外写死的高代价格立方惩罚，避免通道已经可通行，搜索仍因隐藏的过高代价绕数十米。

早期“把 ROG 静态边界回填到全局图以统一边界”的方案已被上述方式替代，不应按旧文档恢复。

## 10. 圆形检查封洞、轻微重叠后反复脱困

**遇到的问题：** 800 mm 洞口被圆形安全半径封住；车身轻触静态格就 blocked；脱困轨迹连起点也不允许重叠；同一位置反复退出而不前进。

处理过程：

- 仿真改成贴合车辆的 16 点多边形，外接范围约 592 × 594 mm，减少圆形近似的过度保守。
- 受限脱困允许从已重叠状态开始，但不能接触新障碍，原有重叠必须受约束地减小，终点仍需通过正常安全检查。
- 修复短退出动作尚未实质移动就被判完成的问题；加入适合全向车的退出方向候选。
- 后来按用户要求引入统一静态重叠容差，而不是只调整脱困触发值：面积比例上限 4%，边缘侵入深度上限 3 cm，必须同时满足。
- 相同容差用于全局、局部、复用和脱困终点；容差内本来安全的静态重叠不应触发反复退出。

历史卡住记录的重叠面积约 0.008～0.012 m²，但那是静态与动态退出上下文的合计，不能全部解释成纯静态重叠。当前约 0.341 m² 的仿真轮廓，4% 对应约 0.0136 m²。

`recovery_server.overlap_min_ratio` 只决定某类脱困是否触发，不等于正常行驶容差。4% 也不是车宽的 4%，3 cm 更不是允许实体撞墙；它们只放宽指定地图边界判定，Gazebo 实体碰撞仍然生效。

全局当前按朝向构建车身通行检查，并不是已实现完整 XY-yaw 联合搜索。斜着接近洞口时的扫掠尺寸、实际柱子和跟踪误差仍可能限制通行。

## 11. 下坡把洞口识别成障碍，南北洞反复绕行

**典型南侧路线：** 从 `(-1.449, -3.943)` 附近平台到 `(2.609, -3.813)`。雷达正对坡下洞口时更容易触发；北侧后来也复现。

已确认并分别处理了以下来源：

1. **错误借用了平台高度。** 远处洞口没看到当地地面，却用机器人所在平台高度计算净空。现在优先使用该格近期验证地面和受限邻域拟合；车身接地切平面只能在近身范围使用。
2. **只有洞顶回波时分类错误。** 引入/完善 `OVERHEAD_GROUND_UNVERIFIED` 处理：局部仍需确认通行，但不只凭未确认状态就把它写成全局确定障碍，迫使大绕行。
3. **5 cm 体素与旧最低回波造成假低顶。** 保存实际回波高度上下界，新一帧有效观测更新该体素的高度范围，不让旧低点永久锁住洞顶高度。
4. **仿真雷达深度采样误差。** 原先 `360 × 96` 扫描在静止时也能测出明显偏低净空。垂直采样提高到 192，并同步真值定位器射线布局；特定北侧路线由失败变为通过。
5. **车身边缘离散误差。** 新增 `dynamic_edge_overlap_tolerance`，限定于显式多边形边缘、指定地面/低净空原因和近零 ESDF 距离。墙体、车身内部障碍、未确认悬空地面、过期查询等不能借此放行。

两个地面证据参数是 `overhead_ground_search_radius: 0.60` 和 `overhead_ground_history_time: 1.0`，分别限制搜索空间和证据时间，不代表可以忽略该范围里的障碍。

降低 `min_headroom_known_ratio` 只针对观测不足；缩小动态障碍触发半径可能推迟绕行，却也可能让局部到洞口才被挡住。这两种调参都不能单独修复上述高度错误。

## 12. 有速度却过不去：场地碰撞与驱动物理

**遇到的问题：** 南侧洞内已经输出约 0.6 m/s，车仍不动；提高上坡速度也不能解决。

接触复测曾在约 `(0.600, -4.329)` 记录到车身顶部持续接触横梁，驱动力从约 85 N 增到 120 N 上限，实际速度仍接近零。该次问题确实来自物理接触，不是规划器没有发速度。

250 mm 洞高配 240 mm 车高只有约 10 mm 名义余量；原三角碰撞网格的数值 margin 约 10 mm，吃掉了这段余量。已将南北洞口四个横梁的 mesh 改为 `optimization="convex_hull"`，其碰撞 margin 约 1 mm，并写入导入脚本保证可复现。

修改后南侧指定路线成功往返。没有通过删除横梁、关闭碰撞或强行穿模解决；但这种 margin 修正属于仿真物理，不能用来保证真实车体与真实洞顶绝不接触。

## 13. 场地视觉、Gazebo 与硬件加速

**需求和处理：**

- 当前使用 Gazebo Harmonic / Gazebo Sim 8 与 ROS 2 Jazzy 链路，不是 Gazebo Classic。
- 最初尝试 Blender 风格场地视觉，用户认为质量不满足要求，随后切换使用 `RM27_Gazebo_Harmonic_part1.tar.xz`、`part2.tar.xz` 提供的场地资产。
- 视觉网格与碰撞网格分开接入，保持坐标一致。Blender 材质负责外观；质量、摩擦、碰撞和雷达回波还取决于仿真配置。
- 更换碰撞模型后，原来被简化场地掩盖的坡道接触、洞顶余量和底盘响应问题暴露出来，因此“更真实”可能同时意味着“原参数不再好用”。
- Gazebo 与 RViz 引入硬件渲染相关启动支持，实车 RViz 也可以使用核显。核显主要加速显示和仿真 GPU 雷达，不会自动加速以 CPU 为主的 MINCO、MPC 和普通 ROS 节点。
- 网格轻量化、减少非必要显示、降低可视化频率、无 GUI 验证可降低负载；雷达采样精度与实时性之间仍有取舍，不能只追求最低采样数。

## 14. 从旧雄安车替换为新 STL 车辆

**用户要求：** 导入 `stl饼哨922.zip`，使用 roll 翻下的约 240 mm 车身，轻量化；后续改用去掉突出线材的 `哨922stl.zip`，雷达 roll 30°；云台对正前方，删除旧车辆模型。

当前模型方向：

- 仿真入口已经使用新车模型，视觉网格与简化碰撞体分离，并同步轮子、传感器与底盘相关尺寸。
- 修正 CAD 到 ROS 的坐标关系、云台正前方以及雷达安装姿态。当前雷达保留相应位置偏置，按当前轴定义使用负 30° roll，修正过最初方向相反的问题。
- 车高相关最高碰撞点调整到 240 mm；并非只把主体 box 压低而保留更高的雷达/附件碰撞体。
- 质量和惯量使用简化模型估计并调试。STL 没有材料密度、真实总重、轮胎摩擦和电机能力，现有约 10.2 kg 总质量及摩擦设置不能称为实车实测数据。
- 当前全向轮接触和驱动仍有简化，所以“以这辆车为基准”不等于完整复现实车动力学。

常用修改位置：

| 想改什么 | 文件或配置 |
| --- | --- |
| 仿真实际车高、碰撞体、质量惯量、驱动参数 | `src/rm_27_stimulation/urdf/simulation_waking_robot.xacro`，车高属性 `folded_vehicle_height` |
| 雷达模型、安装和扫描布局 | 同目录 `mid360.xacro` 及主车 xacro 的安装参数 |

只缩小导航 footprint 或 `vehicle_height` 不会同步缩小 Gazebo 碰撞体。

## 17. 哪些方案已经被替换，哪些结论不能沿用

| 旧方案或容易误解的结论 | 当前应采用的理解 |
| --- | --- |
| 把 ROG 保守静态投影回填全局地图 | 已改为原始 PGM 统一多边形检查，动态来源单独检查 |
| 车身与静态 PGM 必须零重叠 | 当前允许面积与深度同时受限的静态边缘容差 |
| 只调脱困触发比例就能解除 blocked | 正常安全判定、复用、全局和终点必须使用一致容差 |
| 放宽未知格或降低已观测比例就能消除洞口误判 | 它们不能修复错误地面高度、真实低顶或物理碰撞 |
| 提高最低速度一定能上坡 | 遇到保护停止、横梁接触或路线本身不可行，速度辅助无效 |
| 把车高配置改成 235 mm 就把模型改矮了 | 当前实体仍为 240 mm |
| 某轮往返成功，所有停顿已经根治 | 只证明对应路线、定位和图形负载条件下通过 |
| 公共代码同步后实车一定不再发生 | 实车尺寸、传感器误差、驱动力、坐标标定和运行参数仍需验证 |

## 18. 后续最有价值的排查方向

1. 继续定位洞口当地地面证据为何间歇缺失，重点看 `OVERHEAD_GROUND_UNVERIFIED`，而不是继续统一放大所有容差。
2. 处理极短安全前缀与非零起点速度的优化困难，减少反复截断、失败、制动的循环。
3. 对“规划正常但位置不动”同步记录指令速度、实际速度、姿态、规划状态和 Gazebo 接触，先区分控制与物理。
4. 用相同起点、目标、朝向、定位模式和图形负载重复统计，观察成功率、绕行率、途中低速持续时间和平均速度。
5. 实车验证前先统一真实车高、footprint、雷达外参和速度限制的实际含义，避免沿用仿真轻量模型或旧文档中的数值。
