# 2026-10-28 Point-LIO 过洞观测与路径恢复修复

针对用户 20:34—20:36 的运行，以及随后同出生点、同目标的独立复测。在线定位始终使用
Point-LIO；Gazebo 真值只进入独立观察程序，用于实际轨迹、到达误差和时间对齐的定位误差统计。

## 已定位的问题

1. 用户日志中地面未确认、净空不足导致局部路径截断、刹停和脱困。Point-LIO 模式原先直接把
   定位用的下采样 `/cloud_registered` 交给 ROGMap，缺少原始射线栅格中的地面细节和无回波证据。
2. 原始 GPU 雷达对仅约 10 mm 的净空余量仍有数值误差。低洞顶回波及不同扫描积累的高度变化
   会使局部地图出现临界净空阻挡；这不等价于机器人 XY 定位严重漂移。
   进一步对照发现，RMUC2026 实际生效的 Point-LIO 扫描体素已经是 0.10 m，但地图体素仍为
   0.20 m、平面拟合残差门槛为 0.10 m。细化地图、收紧平面门槛后，局部高度一致性与过洞
   结果明显改善。因此不能只归因于 ROGMap，也不能凭厘米级 XY 误差排除高度方向的问题。
3. 原全局路线贴近坡道高程突变边缘，车身角点落入不同地面高度/障碍区域。修改前同路线第一段
   虽然 action 成功，实际在南洞受阻后绕行。只看 action 成功会漏掉此问题。
4. 独立复跑发现起点连接死锁：全局地形避边范围内的实际车身可以安全，但全局搜索将起点移开
   约 20 cm；局部稀疏化仅允许 2 个栅格（10 cm）的连接。因此局部种子一直无效，重叠脱困又因
   车身没有实际重叠而拒绝执行，最终持续 BLOCK。该失败段同戳 XY 误差最大约 2.6 cm。

## 实现

- 新增仿真 `pointlio_scan_registrar`：原始 `/livox/lidar` 与 `/aft_mapped_to_init` 配对，使用
  `T_camera_init_body × T_imu_lidar` 注册到 `/pointlio/registered_scan`。只容许 1 微秒以内的
  时间戳数值舍入差（实测 Point-LIO 的 double 转换出现 1 ns 差），不使用最新位姿替代缺帧。
  队列有界；过期、错帧、无效位姿和不匹配的射线布局拒绝发布。该节点不订阅真值、不发布 TF。
- 复用已测试的有组织扫描无回波重建：只重建具有方向的无穷回波，普通 NaN 不当作空闲射线。
  有限障碍点保留；虚拟端点位于 ROG 射线最大距离之外，只产生空闲证据。
  Point-LIO 定位和停车 GICP 仍使用原来的前端输出。
- 垂直扫描 192 → 288；同步转换器、Point-LIO ring 数、真值适配器及新适配器。根据
  [Ogre2GpuRays::ConfigureCamera](https://github.com/gazebosim/gz-rendering/blob/gz-rendering8/ogre2/src/Ogre2GpuRays.cc#L659)，
  这使第一遍深度纹理由 256 提升至 512。原始消息为 `360×288×32=3,317,760` 字节，保留
  全局定位 worker 原有 4 MiB 上限。384 线的试验因超限启动失败，未采用。
- 仅 RMUC2026 world profile 启用现有地形边缘避让，硬距离 0.50 m、软代价范围 0.70 m。
  全局引导线更靠近坡道内部；实时通行仍经过 ROG 检查。
- 同一 world profile 的 `p_miss` 从 0.45 改为 0.35。单条空闲射线连续更新的回归场景中，饱和
  旧占据证据清为空闲由 18 次降为 6 次。没有射线穿过时不清除；同帧命中优先于所有 miss。
  这不是按超时直接删除障碍，也没有把 UNKNOWN 当作已观测空闲。
- 局部起点连接允许最大 0.30 m（或粗栅格下原有两个单元），覆盖全局避边导致的小范围起点
  移动。连接段须先逐点通过静态和动态完整车身检查；不能越过实际障碍、未知段或无界扩大。
  其余路径继续遵守原全局通行规则。
- 换路进展计时统一使用 ROS 时间，与里程计、地图证据一致；RMUC2026 等待窗口为 4 秒，
  覆盖地图 3 秒保留和扫描确认开销。只约束全局路线替换，不延迟局部刹停；请求存活看门狗
  保持原机制。避免 GUI/仿真低于实时速度时，墙钟先到期而地图尚未更新。

- RMUC2026 的 Point-LIO 地图体素 `filter_size_map: 0.20 → 0.10 m`，平面拟合残差门槛
  `mapping.plane_thr: 0.10 → 0.03 m`。保持已生效的 `point_filter_num: 1`、扫描体素 0.10 m、
  IMU、外参和测量协方差不变。参数写入 world profile；验证的是启动解析后的实际参数。
  原始扫描先做平面滤波的独立试验反而增加停顿，已经撤回，最终版本不包含该滤波。

车高 0.240 m、净空门槛、车身碰撞模型、障碍命中权重、未知区域策略和停车重定位门限未放宽。

## 验证与证据

出生点 `(-9.145,-0.295,0)`，目标依次为 `(9.74,0.79)`、`(-9.45,2.76)`。
每个独立试验重新启动 Gazebo、全局定位并恢复初始朝向；关闭 GUI/RViz，避免图形开销混入导航。
时间采用仿真时间，停车使用实际速度 ≤0.05 m/s，排除起步 2 秒及目标附近 0.35 m。
短停门槛 0.1 秒，长停门槛 5 秒；穿洞要求连续轨迹跨越洞区两侧，单纯绕行不计通过。
定位误差把 `map→base_link` 时间戳与真值插值对齐，不直接用最新 TF 减当前真值。

实验记录在 `tools/global_relocalization/.build/tunnel_observation_fix_20261028/`，包括启动输出、
节点参数/发布者、每段轨迹和事件、输入时间戳审计、抽样扫描、比较 JSON、构建及测试结果。
保留的失败包括 `dense_1`（只换稠密点云，回程超时）、`dense_edge_384`（消息超限），
以及 `final_1`（起点连接死锁，随后修复）、`connector_1`（计时修复前仍绕行）、
`surface_1`（平面滤波使停车增加，方案撤回）；没有删除这些失败或把其后没有执行的路段计为通过。

测试：ROGMap 6 个 CTest 套件、扫描配准/无回波 2 个套件、MINCO 12 个套件全部通过；
启动文件完整 Python 回归另见最终验证结果。
新增回归覆盖起点安全但落在全局缓冲区的恢复、连接中途障碍、过长连接、错误帧/时间戳、
安装变换方向、低障碍保留，以及更快清障时的命中优先。

阶段性结果：`stable_1/2` 已包含观测、避边、起点连接和时钟修复，但保留旧前端地图/平面参数。
它们均完成两段，南洞穿越仍需 6.54 / 7.80 秒，其中低速时间为 3.30 / 3.42 秒。
`lio_fine_1` 验证细化前端后南洞 3.18 秒、北洞 3.66 秒；南洞无短停，回程坡道交界有一次
1.26 秒短停。因此后续采用默认启动入口继续独立复跑，不能只选择这一轮的较好路段。

有限次数仿真不能证明所有地点永无短停，也不表示 Point-LIO 长时间漂移已被解决；
现有静止 GICP 后端继续保留。本轮没有新增连续重定位后端，也没有用真值校正在线定位。

## 最终默认入口复跑

`release_1/2` 均直接使用默认参数启动，未传入试验 YAML。四段 action 均成功，实际轨迹均
穿过目标洞区，无中途绕洞、持续 BLOCK 或超时。真值仅用于以下离线评价。

| 试验 | 全段耗时 / s | 洞区穿越 / s | 全段短停次数（≥0.1 s） | 到达误差 / cm |
|---|---:|---|---:|---:|
| 默认入口复跑 1，目标 1 | 25.20 | 南洞 3.42 | 1 | 7.0 |
| 默认入口复跑 1，目标 2 | 27.92 | 北洞 3.72 | 0 | 2.0 |
| 默认入口复跑 2，目标 1 | 25.31 | 南洞 3.48 | 0 | 9.8 |
| 默认入口复跑 2，目标 2 | 27.02 | 北洞 4.68 | 0 | 2.6 |

四段中唯一短停为 `release_1` 南洞 0.12 秒；两次南洞低速时间均为 0.42 秒，较细化前端前
的 3.30 / 3.42 秒下降。北洞穿越 3.72 / 4.68 秒，不能宣称每一段都快于最初基线。
原始 `baseline` 目标 1 耗时 36.85 秒，但实际上放弃南洞并绕行；最终同目标为 25.20 / 25.31 秒。

注册扫描延迟的 95 分位及对齐后的高度误差见 `height_consistency.json`；所有原始事件及
短停位置见 `comparison.json`。误差存在运行间波动，尤其回程 XY 误差，不能据此宣称已经
解决长时间定位漂移。当前结果支持先修正前端局部几何、地图观测和规划恢复，而非新增后端。

  world:=RMUC2026 navigation_mode:=minco use_ground_truth_odom:=false \
  global_relocalization:=true gui:=true use_rviz:=true
